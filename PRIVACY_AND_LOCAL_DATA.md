# Privacy and Local Data

This guide describes what this project writes locally, how long to keep it, how to clean it up, and what must be preserved when an order outcome or security event is unresolved. It is operational guidance, not legal, tax, records-management, or incident-response advice.

The repository does not contain a database or publisher analytics client. Credentialed use still sends requests to Kalshi, and installation or verification may contact package indexes and vulnerability-advisory services. Those services retain data under their own policies.

## Repo-local data inventory

Paths below are relative to the project root. `.gitignore` reduces accidental Git commits, but it does not encrypt files or stop backup and cloud-sync software.

| Exact path | What it can contain | Sensitivity and lifecycle |
|---|---|---|
| `./.env` | Runtime settings, API key ID, absolute private-key path, mode, acknowledgements, and write flags. It should never contain the private-key body. | Treat as sensitive configuration. Keep only while this working copy is configured; do not share it. |
| `./.public_verify_attestation.json` | Build ID, manifest digest, Python version, verification timestamp, check count, and PASS status. | No credential content by design. Production accepts it for at most 24 hours; it can be deleted and regenerated by verification. |
| `./VERIFICATION_REPORT.md` | Point-in-time check results and diagnostic details from verification. | Review before sharing because filenames, environment details, or failure text may be identifying. Keep the latest useful report or preserve it for an incident. |
| `./CLEAN_EXTRACTION_VERIFICATION.txt` | Clean-package verification output, if a release-preparation workflow captures output under this name. | Review before sharing. It is not required for normal operation. |
| `./TRADING_DISABLED` | The local hard-stop state. | Not personal data. Keep it present except during an intentional, fully authorized demo or production cycle. `purge-local-data` leaves it in place. |
| `./runtime/session_ledger.json` | Tickers, series, outcome/side, count and price, client and reservation IDs, mode, timestamps, status, exchange order/fill fields, and ambiguity reasons. | Account-linked operational evidence. Keep through every unresolved order, fill, position, or dispute. |
| `./runtime/session_ledger.reset-YYYYMMDDTHHMMSSZ.json` | A timestamped prior ledger created by `reset-session-cap`. | Same sensitivity as the current ledger. Reset archives can accumulate and are not rotated automatically. |
| `./runtime/live_instance.lock` | Process ID, hostname, start time, and a random lock token. | Machine-identifying operational state. It normally disappears when the writer exits cleanly. Treat an unexpected lock as evidence until no bot process is running. |
| `./logs/orders.jsonl` | Order-plan fields, timestamps, mode, ticker, client/reservation/order IDs, result, fill/remaining counts, and bounded error text. | Account-linked trading history. Append-only; it has no automatic retention or rotation. |
| `./runtime/` and `./logs/` | The files above plus `.gitkeep` placeholders. | The guarded cleanup command removes regular contents except top-level `.gitkeep` files. |
| `./.venv/`, `./__pycache__/`, and tool caches | Installed packages, bytecode, and local tool state. | Not intended to contain account records, but may expose local paths or usernames. Remove with the working copy during uninstall. |

The private key itself must be outside the repository at the absolute path named by `KALSHI_PRIVATE_KEY_PATH`. It is the highest-sensitivity local item even though it is not repo-local. Never copy it into evidence bundles, logs, screenshots, support tickets, or a synced folder.

Console output is outside the repository but can still be sensitive. Authenticated runs display a reported balance, plans, accepted-order prefixes, and error context. Terminal scrollback, shell transcripts, screen recordings, crash capture, and operating-system backups may retain that output.

## Default retention guidance

The project does not enforce a retention clock. Unless a law, policy, dispute, accounting need, or incident requires longer retention, use this conservative operational default:

- Keep the current ledger and order log until the official account confirms every related resting order, fill, settlement, and position is understood.
- After definitive reconciliation, keep account-linked bot logs and reset-ledger archives for no more than 30 days, then purge them. Review monthly if the working copy remains in use.
- Keep only the latest useful `VERIFICATION_REPORT.md`. The attestation expires for production authorization after 24 hours and can be deleted at any time; verification will recreate it.
- Keep `.env` only while the working copy is configured. Delete it when credentials are revoked or the project is uninstalled.
- Use official account exports—not raw bot logs—as the durable record if financial, tax, legal, or organizational requirements call for longer retention.

Shorter retention is preferable when the data is no longer needed. Do not apply the 30-day default to an unresolved incident.

## Guarded cleanup after normal, reconciled use

First arm the hard stop:

```bash
python run_bot.py kill-switch on
```

Then complete all of these checks:

1. Stop every bot process.
2. In the official Kalshi interface, reconcile resting orders, fills, settlements, and positions—including every accepted ledger entry.
3. Confirm there is no ambiguous or disputed submission and no need to preserve evidence.
4. If `runtime/live_instance.lock` remains, confirm no bot process is running before using the documented `unlock` command.

Run the guarded cleanup only after those checks:

```bash
python run_bot.py purge-local-data --ack I_ACCEPT_PURGING_LOGS_AND_RESETTING_SESSION_STATE
```

The command requires `TRADING_DISABLED` to remain on, the exact acknowledgement, no live-instance lock, and no reserved or ambiguous ledger contracts. It refuses symlinked or unsupported entries. When allowed, it removes regular files beneath `./logs/` and `./runtime/` while preserving their top-level `.gitkeep` placeholders.

This guard is deliberately limited. It cannot prove that every accepted order or official account position is resolved. It also does **not** remove `./.env`, `./.public_verify_attestation.json`, `./VERIFICATION_REPORT.md`, the external private key, terminal history, cloud copies, or data held by Kalshi.

## Safe uninstall

For a normal uninstall with no incident or unresolved trading state:

1. Arm the kill switch, stop all processes, and reconcile the official account as described above.
2. Revoke the demo or production API key through the official provider interface. Record the revocation time if your policy requires it.
3. Run `purge-local-data` while the project is still available to enforce its cleanup preconditions.
4. Delete `./.env`, `./.public_verify_attestation.json`, generated verification output, the virtual environment and caches, and the project working copy.
5. After revocation, remove the external private-key file and any authorized backups under your organization's deletion policy.

Normal file deletion is not guaranteed secure erasure on SSDs, synced folders, snapshots, or backups. Clear recycle bins and cloud version history where appropriate, and follow the storage provider's retention process.

## Incident-preservation exception

Do **not** purge, reset the session cap, edit logs, or uninstall if any of these are true:

- a request timed out or its outcome is ambiguous;
- an order, fill, settlement, or position is unexpected or disputed;
- the key, API key ID, `.env`, machine, or account may be compromised;
- a vulnerability, operational error, legal hold, or reporting obligation is under review.

Instead:

1. Arm `TRADING_DISABLED`, stop all processes, and manage open orders through the official Kalshi interface.
2. Revoke the affected key if exposure is possible. Do not delete or redistribute the private key as “evidence.”
3. Preserve access-restricted, read-only copies of `runtime/session_ledger.json`, all `runtime/session_ledger.reset-*.json` files, `logs/orders.jsonl`, `VERIFICATION_REPORT.md`, `.public_verify_attestation.json`, the original release ZIP/checksum if available, and `MANIFEST.sha256`.
4. Record UTC times, operating system, Python version, release version, actions taken, and official account exports. Hash preserved files so later changes are detectable.
5. Keep the original files unedited and share only redacted copies with the smallest necessary audience.

The cleanup command blocks a ledger with reserved or ambiguous contracts, but software cannot identify every incident. An accepted entry, official resting order, or account position still requires human confirmation.

## Redaction and sharing checklist

Before posting an issue, sending a support bundle, adding a portfolio screenshot, or sharing a reproduction:

- Never include a private key, PEM text, signature, recovery material, or an unredacted `.env`.
- Remove the full API key ID and absolute private-key path.
- Redact order IDs, client order IDs, reservation IDs, balances, positions, fills, trading history, and account-specific timestamps when they are not essential.
- Remove usernames, home-directory paths, hostnames, process IDs, and personal filenames.
- Review error strings and terminal screenshots; cropping a screenshot may leave hidden metadata or surrounding content.
- Search every attachment for `KALSHI_API_KEY_ID`, `KALSHI_PRIVATE_KEY_PATH`, `BEGIN PRIVATE KEY`, `BEGIN RSA PRIVATE KEY`, and account/order identifiers.
- Prefer release version, archive SHA-256, operating system, Python version, expected behavior, observed behavior, and the smallest non-sensitive reproduction.
- If a mutation may have occurred, say so privately and preserve the original evidence. Do not post account evidence in a public issue.

See [SECURITY.md](SECURITY.md) for vulnerability-reporting guidance.

## Cloud-sync caution

Do not run a credentialed demo or production copy from OneDrive, Dropbox, Google Drive, iCloud, a network share, or a broadly shared user profile. Sync tools can upload `.env`, ledgers, logs, lock metadata, and deleted-file versions regardless of `.gitignore`; inherited share links can make later cleanup difficult.

For credentialed use, place both the working copy and its external key in separate, local, access-restricted, non-synced locations. Keep the key outside the repository. If organizational backup is required, use an approved encrypted secret store with explicit access and retention controls—not a general-purpose shared folder.
